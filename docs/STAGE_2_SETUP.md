# Настройка этапа 2

> Историческая инструкция этапа 2 (протокол v2). Текущая версия использует предметную схему и протокол v3: см. [DATABASE_SETUP.md](DATABASE_SETUP.md). Для уже настроенного проекта с profiles/sync_records нужна только миграция 003, без повторного выполнения 001/002.

Приложение работает без аккаунта и без параметров Supabase. Реальные записи хранятся в Room, а примеры открываются отдельно через настройки. Личный ключ Token Harbor вводится только в приложении.

## Supabase: учебный проект

1. Создай отдельный тестовый Supabase-проект.
2. Открой **Authentication → Sign In / Providers → Email**. Включи Email provider, отключи **Confirm Email**, сохрани изменения. Разреши новые регистрации (**Allow new users to sign up**). В старом интерфейсе раздел может называться Providers.
3. Для этого прототипа SMTP, magic links, OTP и восстановление пароля по email не используются. Адреса не проверяются: можно зарегистрировать чужой/ошибочный email; автоматического восстановления доступа нет. Это настройка учебного проекта, не рекомендация для production. [Официальная конфигурация](https://supabase.com/docs/guides/auth/general-configuration), [ограничения тестирования email](https://supabase.com/docs/guides/auth/testing-auth-flows).
4. Через SQL Editor тестового проекта примени `supabase/migrations/001_core.sql`, затем `002_local_first_sync.sql`. Не запускай миграции повторно: таблицы/политики/триггеры создаются один раз. При использовании CLI — обычный последовательный `supabase db push` для тестового окружения.
5. В настройках проекта возьми **Project URL** и **publishable key** (`sb_publishable_…`). Допустим старый `anon` JWT с ролью `anon`. Никогда не используй `service_role` или `sb_secret_…`.
6. В локальном, не отслеживаемом `local.properties` укажи:

```properties
sdk.dir=D\:/andriodsdk
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
```

Это публичная конфигурация клиента, а не личный ключ ИИ. Можно задать одноимённые переменные среды. Пересобери APK: настройки попадают в BuildConfig. Ошибочная/пустая конфигурация отключает вход, сохраняя рабочий локальный режим. Сборка отвергает известные форматы серверных ключей; клиент дополнительно проверяет тип публичного ключа.

Имя передаётся стандартной регистрации в `user_metadata.display_name`; триггер создаёт `profiles` с `user_id = auth.users.id`. Пароль отправляется только в HTTPS-запросе Supabase Auth и не сохраняется приложением. Access/refresh token находятся в зашифрованном noBackup-хранилище; обновление refresh token сериализовано. При истёкшем входе записи аккаунта остаются доступны офлайн; повторный вход нужен для синхронизации. [Сессии Supabase](https://supabase.com/docs/guides/auth/sessions), [HTTP API Auth](https://supabase.com/docs/reference/self-hosting-auth/get-a-user).

## Перенос и облачные записи

После входа, если на устройстве есть личные локальные записи, появится отдельное предложение. **Синхронизировать** копирует их в пространство вошедшего пользователя, сохраняя UUID, даты и связи; исходные локальные записи не удаляются. Повтор безопасен. **Не сейчас** оставляет активными записи устройства. Вернуться к переносу и переключиться между устройством/аккаунтом можно в настройках.

Выход удаляет сохранённую сессию и переключает интерфейс на записи устройства. Данные аккаунта в Room сохраняются, но другому аккаунту не показываются. Повторный вход в тот же аккаунт открывает его кеш. Личный ключ ИИ относится к устройству и сохраняется при выходе, поскольку ИИ не привязан к аккаунту.

Облако использует `sync_records` и RPC `sync_push`/`sync_pull`, привязанные к `auth.uid()`. Клиент не может писать в таблицу напрямую, обходя проверку версий. Политики RLS ограничивают чтение; RPC явно проверяет пользователя, версии, ссылки и неизменяемость исходника. [RLS Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

Миграция 002 сохраняет таблицы 001, переносит их существующие записи с UUID/датами/связями в единое версионированное хранилище и делает старые таблицы записей доступными клиенту только для чтения. Старый `confirm_capture` больше не используется новым клиентом. Профили сохраняют существующие политики. Изменения исходных таблиц внешними legacy-клиентами после миграции не поддерживаются; согласуй переход, если такие клиенты появились.

Синхронизация отправляет изменения, затем получает все страницы облачных записей, включая отметки удаления. Версия определяет конфликт; часы устройства не используются для автоматического выбора победителя. При конфликте видны обе копии, выбор явный. До согласования запись не перезаписывается. После выбора обе версии остаются в локальной истории. Tombstone скрывает запись из UI и передаёт удаление другим устройствам; физическая очистка серверных tombstones/резервных копий не входит в этот прототип.

WorkManager хранит задания с условием подключения к сети и повтором с увеличением задержки. При входе/локальных правках есть немедленное задание, для получения чужих изменений — периодическая проверка с минимальным интервалом 15 минут. Android может откладывать фоновую работу; мгновенное выполнение не гарантируется. После force-stop фоновые задания возобновляются после следующего открытия приложения. [Официальная документация WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

## Token Harbor BYOK

Открой **Настройки → Искусственный интеллект → Настроить ИИ**, введи свой ключ, сохрани и нажми **Проверить подключение**. Не присылай ключ в чат и не добавляй его в свойства сборки, SQL или Git.

Проверка — `GET https://tokenharbor.ai/v1/models` с Bearer-ключом. Этот маршрут требует ключ и возвращает актуальные вызываемые ID моделей. Модели не выдумываются и не зафиксированы в коде: приложение показывает идентификаторы из ответа сервиса. Генерация, анализ, отправка личных записей и транскрибация не вызываются. Успешная проверка каталога не подтверждает наличие средств или доступность генерации каждой модели. [Документация Token Harbor о каталоге](https://status.tokenharbor.ai/docs/api/models), [основная документация](https://tokenharbor.ai/docs).

Владелец ключа оплачивает использование провайдера по его условиям. Ключ можно заменить/удалить; ручные функции продолжают работать. После сохранения поле очищается, сохранённый ключ никогда не подставляется обратно в форму. После перезапуска показывается «Ключ сохранён · ещё не проверен», без фиктивного сетевого успеха.

AES-256-GCM использует новый IV при каждой записи, AAD разделяет сессию и ключ провайдера. Ключ шифрования хранится в Android Keystore, шифротекст — в `noBackupFilesDir` через AtomicFile. Облачные резервные копии и перенос данных Android исключены правилами манифеста. Токены/ключи отсутствуют в Room и payload синхронизации. Аппаратная защита зависит от устройства; защиты от полностью скомпрометированной ОС не обещаем. [Android Keystore](https://developer.android.com/privacy-and-security/keystore).

## Локальные проверки

```powershell
$env:JAVA_HOME='D:/andriodstudio/jbr'
./gradlew.bat assembleDebug assembleDebugAndroidTest testDebugUnitTest lintDebug --offline --no-daemon --no-watch-fs --console=plain
```

SDK Platform 35, minSdk 26. При первом получении зависимостей убери `--offline`. Сохранены AGP 8.7.3, Kotlin 2.0.21 и Compose BOM 2024.10.01. Добавлены Room 2.6.1 и WorkManager 2.10.0 из совместимого установленного кеша; это фиксированные проверяемые версии, не заявление об актуальности последних релизов. [Room](https://developer.android.com/jetpack/androidx/releases/room), [WorkManager](https://developer.android.com/jetpack/androidx/releases/work).

Для локальной проверки настоящего PostgreSQL/RLS без Supabase:

```powershell
npm install --prefix .tools/sql-node --ignore-scripts @electric-sql/pglite@0.5.13
node supabase/tests/run-local-sync.mjs
```

Тест создаёт отдельную базу в памяти, роли/имитацию `auth.uid()`, применяет обе миграции и проверяет SQL. Это не проверка реального сервиса Auth, PostgREST или инфраструктуры Supabase. [PGlite](https://pglite.dev/docs/).

Для Android UI/process-тестов нужен **отдельный эмулятор с тестовыми данными**. Сценарии ввода/перезапуска намеренно требуют `sbros_isolated=true` и проверяют, что устройство — эмулятор. Остальные тесты базы создают собственные временные БД; криптотест использует отдельные файлы/alias.

```powershell
adb -s emulator-5554 install -r app/build/outputs/apk/debug/app-debug.apk
adb -s emulator-5554 install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb -s emulator-5554 shell am instrument -w -r -e sbros_isolated true ru.sbros.app.test/androidx.test.runner.AndroidJUnitRunner
```

Для фактического перезапуска процесса запусти `ProcessPersistenceTest#a_seedBeforeForceStop`, заверши процесс через `adb shell am force-stop ru.sbros.app`, затем отдельно `ProcessPersistenceTest#b_verifyAfterForceStop` с тем же аргументом `sbros_isolated`.

Перед production обязательно повторить миграции и межпользовательские тесты в настоящем тестовом Supabase, проверить регистрацию двух аккаунтов, сеть off/on, refresh/logout и серверные ограничения. Учётные данные и живой ключ ИИ в комплект не входят.
