# Supabase: переход на предметную схему

Протокол синхронизации **v3**, атомарное подтверждение разбора через **sync_confirm_capture_v1**.

Если миграция 005 уже применена, сейчас нужна **только новая миграция**:

`supabase/migrations/006_project_lifecycle.sql`

Она добавляет состояние завершения проекта и признак предложения завершить его после выполнения шагов. Таблицы, аккаунты и существующие записи сохраняются. До неё должна быть применена миграция 005.

Если у тебя пока только `profiles` и `sync_records`, последовательно выполни 003, 004, 005 и 006 из `supabase/migrations/`. Уже применённую 003 повторять нельзя.

## Что сделать сейчас

1. Закрой приложение «Сброс» на телефоне на время перехода.
2. В PowerShell выполни следующую команду. Она только копирует SQL в буфер обмена; команду можно выполнять из любой папки:

```powershell
Get-Content -Raw -Encoding UTF8 'C:\Users\admin\Downloads\SbrosAndroid\supabase\migrations\006_project_lifecycle.sql' | Set-Clipboard
```

3. Открой **свой текущий проект Supabase → SQL Editor → New query**. Вставь SQL через **Ctrl+V**, запусти **Run**. Используй обычную административную роль SQL Editor (`postgres`). [SQL Editor и таблицы](https://supabase.com/docs/guides/database/tables).
4. Файл 006 добавляет колонки `projects.completed_at` и `projects.completion_ready`, обновляет представление и внутреннюю функцию обмена. Он не удаляет данные. Атомарное подтверждение из 005 сохраняется.
5. Дождись успешного выполнения всего файла. Он выполняется одной транзакцией: ошибка откатывает изменения. При ошибке остановись и сохрани её полный текст; не запускай части скрипта отдельно.
6. В Android Studio нажми **▶ Run app**, чтобы установить новую версию приложения. В корне открыт тот же проект; `local.properties`, URL Supabase и публичный ключ менять не требуется.
7. Открой **Настройки → Аккаунт → Синхронизировать**. Если работал в локальном режиме, выбери **Добавить записи в облако** и подтверди перенос.

Обычные правки используют `sync_push_v3` / `sync_pull_v3`, а первое подтверждение разбора — `sync_confirm_capture_v1`. После применения 006 обнови приложение на всех устройствах. При первой синхронизации после запуска приложение проверяет `sync_schema_version()`: до применения 006 записи остаются локально, чтобы прежняя функция не потеряла новый статус проекта.

Если один сброс независимо подтвердили на двух устройствах, второй набор результатов не загружается частично. В настройках аккаунта появится конфликт. Можно оставить облачный разбор или вернуть свой вариант во входящие для повторного решения. Обе версии и локальные результаты сохраняются в истории. Возврат во входящие сам по себе не создаёт повторные дела.

## Что появится в Table Editor

| Таблица | Данные приложения |
|---|---|
| `profiles` | Имя и ID пользователя Auth |
| `captures` | Полный исходный текст, статус входящих/подтверждения, связь с родительским сбросом |
| `projects` | Проект, сфера, желаемый результат, источник, дата явного завершения и предложение завершить проект |
| `tasks` | Дело/шаг проекта, статус, сложность, срок, источник и проект |
| `thoughts` | Дневник/идея, текст, избранное и источник |
| `events` | Событие, дата, время и источник |
| `materials` | Справочные материалы и источник |
| `analysis_runs` | Модель, итог попытки разбора, даты, число предложений, безопасный код ошибки |

`analysis_runs` заполняется после новых попыток ИИ, а не задним числом. `succeeded` означает, что получен и сохранён проверенный разбор; пользовательское подтверждение отражается отдельно в `captures.status`.

Во вкладке представлений также будут:

- `calendar_entries` — события и сроки задач, без создания дубликатов;
- `sbros_sync_projection_v3` — техническое представление для обмена с Android. Оно собирает JSON из обычных колонок и не хранит вторую копию данных.

Миграция 003 заменяет `sync_records`, `items` и прежние версии `captures`/`weekly_reviews`; миграция 004 окончательно удаляет недельные обзоры. Исходные записи из `sync_records`, их UUID, версии, даты и связи переносятся в новые таблицы. Auth и профили остаются. Поля `theme` и `palette` удаляются из профилей: приложение хранит оформление локально.

## Данные телефона

- Удалять приложение, чистить его данные или выходить из аккаунта не требуется.
- Room остаётся локальным источником данных. Его существующая таблица записей сохраняется; синхронизация преобразует локальную модель в типизированные облачные таблицы через RPC.
- Перенос записей устройства в аккаунт по-прежнему требует согласия. Чтобы сохранить связи, вместе с живыми результатами переносятся необходимые пометки удаления их исходников/проектов.
- Черновик ввода и неподтверждённые карточки разбора остаются только на устройстве.
- Ключ Token Harbor остаётся в зашифрованном хранилище Android. В SQL, `profiles`, `analysis_runs` и сетевой обмен с Supabase он не включается.
- Исходное аудио приложение не сохраняет.

## Повторный запуск и новый проект

`003` применяется один раз. Если `sync_records` уже отсутствует после успешного перехода, повторять скрипт не нужно.

Для совсем нового проекта с пустой схемой последовательно примени файлы 001–006 из `supabase/migrations/`. Для текущего настроенного проекта **не повторяй 001–003**.

## Границы выполненной работы

Подготовлены SQL, новый клиентский протокол и журнал попыток ИИ. Живой Supabase из этой сессии не изменялся. По просьбе пользователя не запускались сборка, SQL/Android-тесты, пробные запросы к облаку и скриншоты. Старые локальные SQL-тесты этапа 2 относятся к протоколу v2 и не подтверждают работу новой миграции.
