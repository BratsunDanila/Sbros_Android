# AGENTS.md — ОБЯЗАТЕЛЬНО прочитать перед кодом

## Актуализация: предметная схема Supabase v3
Последующими заданиями пользователь разрешил и получил SpeechRecognizer, полный BYOK-разбор и переход на отдельные облачные таблицы. Действующий SQL: `supabase/migrations/003_relational_domain.sql` после 001/002, затем `004_remove_weekly_reviews.sql` и `005_atomic_analysis_sync.sql`. Недельный обзор удалён: осталась только UI-плашка актуальности с галочкой, без истории и таблицы. Клиент вызывает `sync_push_v3` / `sync_pull_v3`, подтверждённый разбор отправляет через `sync_confirm_capture_v1`; `sync_records` больше не является хранилищем. Источник настройки: `docs/DATABASE_SETUP.md`, модель и ER-диаграмма: `docs/DATABASE_ARCHITECTURE.md`. Room и необязательный аккаунт сохраняются; ключ ИИ — только Keystore. Пользователь просит не запускать тесты, сборку и скриншоты в текущей работе; эту установку учитывать до её изменения пользователем. Описания ограничения этапа 2 «только проверка подключения» ниже исторические и заменены последующими заданиями.

## Уточнение пользователя: этап 2 (актуальный приоритет)
Новое задание **local-first** заменяет прежние пункты ниже об обязательном аккаунте и исключительно серверном ключе ИИ. Room — основной источник записей; аккаунт Supabase необязателен и нужен для синхронизации. Локальные записи загружаются только после согласия. Личный BYOK Token Harbor вводится в приложении, шифруется Android Keystore и никогда не попадает в Supabase/APK/логи/backup. На этом этапе разрешена только проверка подключения, без разбора и транскрибации. Применяется v15. См. `docs/STAGE_2_ARCHITECTURE.md` и `docs/STAGE_2_SETUP.md`. Остальные требования безопасности и визуального соответствия сохраняются.

Ты — инженерный агент, создающий **нативное Android-приложение «Сброс»** на Kotlin + Jetpack Compose. Этот каталог — единый источник требований.

## Непереговорные требования
- **Не заменять нативный UI WebView**: Compose + Kotlin, HTML используется ТОЛЬКО как дизайн-референс.
- Не «улучшать» внешний вид на свой вкус. Не добавлять верхние служебные слоганы, удалённые в v14 clean.
- Ровно 5 нижних пунктов в порядке: **Дела | Мысли | Сброс | Календарь | Обзор**. Микрофон в центре не должен выступать над навигацией и быть чрезмерно большим. Сохранить плавное выделение.
- Приоритет: эстетика и низкий порог входа. Информационная сложность скрыта за конкретными действиями.
- Единая точка ввода: **«Сброс»**. Ввод текстом или через Android SpeechRecognizer, просмотр расшифровки и правка текста.
- Процесс: **сохранить оригинал -> запросить анализ -> показать структурированные предложения -> позволить редактировать/удалять/переклассифицировать -> явное подтверждение -> атомарная запись результатов**.
- Без подтверждения никакого добавления задач/идей/событий из ИИ-предложений.
- Не превращать эмоциональные размышления и дневник в задачи автоматически.
- Обязательные экраны онбординга/приветствия, регистрации, входа, восстановления сессии, выхода из аккаунта.
- Supabase Auth + Postgres/RLS; Token Harbor через **серверную Supabase Edge Function**, API-ключ не должен попасть в APK или Git.
- Настоящие запросы нельзя тихо заменить симуляцией. Пока секреты не настроены — показывай понятное состояние «Не настроен ИИ», оставляй рабочую ручную сортировку и отмечай заглушки явно.
- Исходный HTML хранит данные в localStorage и использует эвристики — это демонстрация, **не переносить такой storage и эвристический разбор как реальную серверную реализацию**.
- По всем асинхронным операциям нужны loading/error/retry/empty states и невозможность двойной отправки.
- Работать малыми проверяемыми вертикальными срезами. После каждого этапа — отчёт: что реализовано, как собрать и проверить, что осталось.

## Порядок задач
Используй `docs/IMPLEMENTATION_PLAN.md`. Сначала создай запускаемый Android Studio проект и авторизацию. Потом пять экранов с локальными фикстурами, затем Supabase, затем полный capture-flow, потом AI/STT. Не пытайся одним гигантским коммитом реализовать всё.

## Правила неопределённости
- Версии библиотек, фактические модели Token Harbor, совместимость structured output и конфигурация Google SpeechRecognition могут меняться: **проверь официальную документацию**, не выдумывай модели/эндпоинты/ключи.
- Если недостаёт URL/ключей проекта, создавай `.env.example`/`local.properties.example`, объясни, какие значения пользователь задаёт самостоятельно, и продолжай с компилируемым локальным состоянием.
- Не печатай и не коммить секреты. Не проси присылать ключ Token Harbor в чат.
- Схема `001_core.sql` — рабочий базис, но нужна проверка в тестовом Supabase и RLS-тесты перед production.
